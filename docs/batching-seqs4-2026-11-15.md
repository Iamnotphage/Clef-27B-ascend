# seqs4 批处理评估：吞吐、质量与 S1 不变性（2026-11-15）

在同一 s1 配置（TP2/4096/eager/缓存关/BF16，GDN 决策 prefill 开启）上只把 `--max-num-seqs` 从 1 改为 4，客户端按 C1/C2/C4/C8/C16 各跑一次全量 2,352 题，逐题保存概率并用作者评分器重算。

关键事实：

- **C1 与 C2 逐位一致**：seqs4 在单并发下的计算路径与 seqs1 完全相同；S1（单并发 P95）与任何 C1 质量评测**不受影响**。
- **C4 起出现批内差异**：批内位置导致的概率迁移开始显现；C4 的 Capability 略升（翻转相互抵消），C8/C16 下降约 0.2。

- 与 2026-11-14 的 seqs4 结果（Capability 74.200、4 条 choice 变化、max 0.097399）一致，说明批内数值效应可复现。

## 3. 对提交的含义

1. **S1 不变**：S1 是单并发 P95；seqs4 在 C1 下 batch=1，输出与 seqs1 逐位一致（本轮 C1 已验证 max 0.0）。因此把 `--max-num-seqs` 设为 4 **不会改变 S1 或 C1 质量结果**。
2. **S2 收益**：C8 达到 **14.049 decisions/s（2.34×）**；这是单次全量运行的吞吐，已被 C8/C16 两点相互印证。
3. **质量边界**：只在真正合批（C4+）时出现；若主办方质量评测为单请求，这项代价不会进入质量分；若在同并发下评测，则按 C8 的 −0.230 Capability / max 0.0974 记录，对应你此前“0.097 可接受”的口径。
4. **批证据**：C1→C8 吞吐 2.34× 无法由排队解释；C16 服务日志出现 `Waiting: 8 reqs`；C1/C2 逐位、C4 起差异，三者共同证明合批真实发生。

## 4. 建议

- **提交服务配置改为 `--max-num-seqs 4`**：S1 与 C1 质量不变，S2 从 5.7 提升到 14.0 decisions/s。
- S2 报告采用 **C8**（14.049 dec/s，p95 950.7 ms）；C16 仅作饱和点记录。
- 质量报告保留两组：C1（提交质量，逐位一致）与 C8（合批质量，−0.230 / max 0.0974），由最终规则决定采用哪一组。
- 批内数值效应仍是 CANN/GEMM 层问题；若后续要求“合批也逐位一致”，需要 batch-invariant 内核，不在本轮范围。

## 5. 边界

- 每个并发点单次全量运行；批内配对取决于到达时序，翻转的具体样本会随运行变化，最大概率差稳定在 0.097–0.103。
- 本轮缓存关闭，未启用 schema cache v2；C8 已达 14.05 dec/s，与 2026-11-14 的 13.76 dec/s（cache v2 开）相当。
- 未测 ERQA 的合批质量；ERQA 质量按 C1 提交口径不受影响，合批 ERQA 需另测。

### 结论

- **批处理下 INT8 的收益终于显现**：C8 吞吐 +5.1%（14.771 vs 14.049），p95 −12.3%（834.0 vs 950.7）——批内 MLP 转为计算受限，INT8 cube 生效。
- **但质量代价不可接受**：叠加后 Capability 73.6987（−0.727）、max 0.269、14 条 choice 翻转、9 条 noul 跨 0.5，远超 0.097 口径。
- **NZ 格式在 C1 反而更慢**：4.961 vs 6.000 dec/s，与另一会话的 ND 候选（C1 +0.28%）相反——NZ 的格式转换/调度在单请求下拖累明显；ND 才是可用的布局。
- 因此 **seqs4 + W8A8(NZ) 不采用**；当前最优质量/性能点是 **seqs4 + BF16（C8 14.049，74.195，max 0.0974）**。

### 若要继续 MLP 量化

唯一可行路径是 **W8A8 + 激活平滑 + ND 格式**：平滑把最坏层局部误差从 11.8% 压到 2.4%（见 `mlp-w8a16-2026-11-15.md`），ND 修复 C1 的格式惩罚；目标是在 C8 保留约 +5% 吞吐，同时把 Capability 损失压回 0.1 以内。该实现需要逐层激活捕获、把 `1/s` 折进 MLP 前 RMSNorm、重新量化转换，预计约 2 小时。
