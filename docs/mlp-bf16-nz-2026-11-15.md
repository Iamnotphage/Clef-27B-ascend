# MLP BF16 NZ 权重格式局部实验（2026-11-15）

在 HBM 微基准（纯读 1.26–1.32 TB/s，MLP 名义 0.53 TB/s）之后，验证 BF16 权重从 ND 预打包为 FRACTAL_NZ29 是否能提高局部 MLP 链的有效带宽。

## 方法

- 脚本：`runtime/probe_mlp_nz.py`
- 权重/输入：复用 `probe_mlp_ffn.py` 的真实 TP2 权重切片与 `mlp-20261115-1027/capture` 的真实层输入（`od-0105` 307 token、`od-0677` 1595、`erqa-0167` 10294；401/512/662/969/1024 为 `od-0677` 前缀）
- 设备：`npu:0`；layer 0/31/63、rank0
- 格式：`allow_internal_format=True`，`torch_npu.npu_format_cast(weight, 29)`；运行前用 `torch_npu.get_npu_format` 断言 ND=2 / NZ=29
- 链：`F.linear → npu_swiglu → F.linear`
- 计时：
  - `warm`：重复调用同一组常驻权重（旧局部探针的口径）
  - `cold`：每次调用前用 256 MiB 读驱逐 192 MiB L2，近似服务逐层流式读权重
- 输出：每次 ND/NZ 输出比较，`bit_equal`、max abs、relative RMSE

## 解释

1. **NZ 是真实收益，不是 L2 假象**：cold 模式每次用 256 MiB 驱逐 L2，307 token 仍有 1.26–1.32×；warm 与 cold 接近。
2. **短序列是 memory-bound**：307 token 时名义 509–532 GB/s，NZ 提到 671–677 GB/s（约 HBM 纯读的 53%），说明 ND 的搬运/重排效率确实受限。
3. **969 token 已转为 compute-bound**：MLP 链 259 GFLOP / 1.012 ms ≈ **256 TFLOPS**；1595/10294 约 282/299 TFLOPS，接近 BF16 Cube 的实际平台。此时名义权重带宽只有 264–280 GB/s，不是 HBM 限制，NZ 只剩约 6%/3%/0%。
4. **对 S1 P95 的影响有限**：S1 P95 输入 969 token，NZ 局部 MLP 1.06×，按 64 层估算每请求约省 **3.8 ms**（0.059 ms/层 ×64），约为 198.42 ms 的 **1.9%**。对 P50（约 401 token）约 1.8%，对 307/512 短请求约 3.5–4.9%，对 1595+ 接近 0。
5. **因此“MLP 是 memory-bound”只适用于短序列**；S1 P95 的 MLP 已经是 compute-bound，继续 tiling/L2 不会显著改善 P95，NZ 是质量中性的约 2% 候选，而不是 7% 级别的优化。

## 决定

- **保留为质量中性的 S1 候选**：需要在服务加载后把 MLP 的 `gate_up_proj`/`down_proj` 权重一次性 `npu_format_cast` 到 NZ29，再跑 6 对服务级 A/B；局部输出逐位一致，预期 P95 约 2%、P50/均值略高。
- **不把它当作 S1 的主要杠杆**：P95 969 token 的 MLP 已 compute-bound；若要把 P95 再降，需要 INT8 Cube（W8A8/W4A16）或提高 Cube 利用率，前者仍有质量代价。
- **S2（seqs4 C8）**：MLP 计算受限，NZ 的权重格式收益更小；W8A8 + 平滑仍是主要候选，但质量门槛未过。
- **下一步**：若接受约 2% P95 的质量中性收益，做服务级 NZ 补丁 + 6 对 A/B；否则把 NZ 作为已归档的局部候选，不进入提交。
