# QKV norm v3 尝试（2026-11-17）

## 结论

- 目标：把 `ClefGdnQkvNorm` 从 v2 的逐行 `ReduceSum` 改成 tile 级归约，并去掉 V 的 BF16→FP32→BF16 两次 Cast。
- 本轮只实现了 **V 直拷**：在 `ProcessTile` 的 `!normalize` 分支用 VECOUT 队列 + UB→UB `DataCopy` 直接写 BSND V，跳过两次 Cast 和 FP32 缓冲。
- 单算子 probe（967 token）：v2 **0.1256 ms**，v3 **0.1249–0.137 ms**，**持平**（约 2× vs baseline）；V `bit_equal=true`、max_abs 0；Q/K 仍为 1 ulp（max_abs 0.001953125，与 v2 相同）。
- 服务全量 S1（cache + MLP NZ + v3 QKV）：**165.54 / 166.06 ms**；MLP-NZ 基线 165.5–166.0 ms，**P95 无收益**。p50/mean 两次为 111.7/121.1 与 120.5/126.7，跨运行漂移大于差异。
- 全量 2,352 条响应与 v2 **逐位一致**（max 0.0、0 choice flips），质量中性。
- 不采用；repo vendor 已恢复 v2（kernel `.o` SHA-256 `e0ca1454…`）。v3 源码归档在 `runtime/qkv_norm_v3_kernel.cpp`。

## 为什么 V 直拷没有收益

- 同条件 probe 下 v2 与 v3 都在约 0.125 ms，说明 v2 的两 次 Cast 不是瓶颈；QKV norm 的时间主要花在 Q/K 的 **T×16 次逐行 `ReduceSum(128)`** 上。
- 服务 p95 对 QKV norm 的节省不敏感：该 kernel 的 4.66 ms/请求（967 profile）很可能与通信/相邻层重叠，端到端窗口由 MLP/GDN/通信主导；单算子省下的部分未进入 p95 关键路径。
- 真正的 v3 需要把逐行 `ReduceSum` 换成 `WholeReduceSum` 的 tile 级归约；v1/v2 已记录 int mask 的 UB 对齐异常与 uint64 mask 返回 NaN，仍需要正确的 repeat/stride 和尾部处理，且预期端到端 ≤1%。
