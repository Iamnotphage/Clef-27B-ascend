# A3 单逻辑 NPU HBM 带宽微基准（2026-11-15）

MLP 的 profile 显示 `aic_mte2_ratio≈0.994`、有效权重带宽约 0.53 TB/s，但一直无法判断这是 HBM 上限还是 MTE2 效率问题。本微基准直接测量同一逻辑 NPU 上大块连续数据的实际读写带宽，用于回答这个问题。

## 方法

- 脚本：`runtime/hbm_bandwidth_probe.py`
- 设备：`npu:0`、`npu:1`（A3 单物理卡内两个逻辑 NPU）
- 工作集：64、256、512、1024 MiB BF16；64 MiB 可落入 192 MiB L2，只作对照，不用作 HBM 结论
- 用例：
  - `copy`：`y.copy_(x)`，读 N + 写 N
  - `sum`：AI Core 归约，读 N + 写 1 个标量
  - `add_out`：`torch.add(x, 1.0, out=y)`，读 N + 写 N
- 每点预热 5 次、正式 20 次，NPU 同步后取单次中位时间
- 运行时 8000 端口 baseline 服务空闲但占用 HBM；最大工作集 2 GiB，未触发 OOM，未发现服务请求

## 结果

单位 GB/s（十进制，按实际读写流量计）：

| 设备 | 大小 | copy | sum（读） | add_out |
|---|---:|---:|---:|---:|
| npu:0 | 256 MiB | 1257.1 | 1256.5 | 1226.7 |
| npu:0 | 512 MiB | 1266.1 | 1302.0 | 1235.1 |
| npu:0 | 1024 MiB | 1274.0 | **1322.2** | 1256.2 |
| npu:1 | 256 MiB | 1261.3 | 1289.8 | 1234.2 |
| npu:1 | 512 MiB | 1266.3 | 1300.2 | 1234.7 |
| npu:1 | 1024 MiB | 1274.5 | **1324.4** | 1254.0 |
| npu:0 | 64 MiB（L2） | 3770.8 | 1449.3 | 2985.2 |
| npu:1 | 64 MiB（L2） | 4600.4 | 1465.9 | 3065.2 |

- 超过 L2 后，两个逻辑 NPU 的纯 HBM 读带宽稳定在 **1.26–1.32 TB/s**；读写拷贝约 **1.26–1.27 TB/s**。
- 64 MiB 的 copy 3.8–4.6 TB/s 是 L2 命中，不代表 HBM。

## 对 MLP 的含义

- MLP 有效权重带宽 **0.53 TB/s**，仅为纯 HBM 读带宽的 **约 40–42%**。
- `aic_mte2_ratio≈0.994` 说明 MTE2 一直忙，但**没有达到 HBM 峰值**；瓶颈更可能是 MTE2 的访问效率（ND 布局、搬运粒度、tiling、L2/格式），而不是 HBM 本身。
- 按 1.27 TB/s 粗算：gate/up 11.4 GB 约 **9.0 ms**（当前 21.34），down 5.7 GB 约 **4.5 ms**（当前 10.73），MLP 合计约 **13.5 ms**（当前 32.07），理论上限可省约 **18.5 ms/请求**（约 9% 的 198.42 ms）。
- 这是上限，不是可直接兑现的收益：纯读/拷贝使用大块连续访问，matmul 还受 Cube L0 tiling、数据依赖和双缓冲限制；但 0.53 与 1.27 之间的差距足以说明 MTE2 效率值得优先实验。

## 下一步

1. **BF16 NZ 权重预打包**：W8A8 NZ 的局部 MLP 比 ND 快，说明格式影响明显；先做 BF16 NZ 的局部 MLP 探针（真实输入、layer0/31/63），再决定服务级 A/B。
2. **MLP tiling / 预取**：在真实 `[307,5120]×[5120,17408]` 形状上比较不同 tile、双缓冲和 L2 预取；目标是把有效带宽从 0.53 提到 0.8+ TB/s。
3. **量化仍是并行路线**：W8A8 + 平滑、W4A16 的收益上限仍高于纯 tiling；若 MTE2 效率提升与量化叠加，收益可进一步放大。
4. **复测条件**：本基准在空闲 baseline 服务旁运行；若要做严格的 kernel 级归因，建议在独占 NPU 上复测一次。
