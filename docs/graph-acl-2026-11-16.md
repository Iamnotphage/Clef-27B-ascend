# Graph / ACL graph 可行性测试（2026-11-16）

> **2026-11-16 补充：** 本文初版使用的是 `cudagraph_capture_sizes=[1]`，实际请求 307/967 token 时**没有 replay**，因此“graph 无收益”的结论只适用于该配置。显式捕获 `[307,967]` 后的复核见第 6 节：短请求 307 token 快 14–21%，但全量 S1 P95 反而变差；最终仍**不采用**，但结论已修正为“graph 仅适合短请求，不适合 S1 P95”。

目标：验证 vLLM-Ascend 在 BIC S1 pooling 服务上能否启用 ACL graph，并测量它能否降低 64 层 eager dispatch。初版结论（capture size=1）：**可以启动、冻结 8/8，但没有收益**；307 token 反而比 eager 慢约 5–6%，967 token（S1 P95）基本持平。不采用。显式捕获尺寸后的修正见第 6 节。

## 1. 配置

- 直接 vLLM 启动，**不加 `--enforce-eager`**；TP2/BF16/pooling/4096/seqs1/缓存关；
- BIC 环境：`CLEF_GDN_DECISION_PREFILL=1`、`NO_RECOMPUTE=1`、`BSND=1`、`SKIP_INITIAL_STATE=1`、`SKIP_CONV_STATE=1`；
- vLLM 日志：
  - `Pooling models do not support full cudagraphs. Overriding cudagraph_mode to PIECEWISE.`
  - `cudagraph_mode=PIECEWISE`、`cudagraph_capture_sizes=[1]`；
  - 每 rank `torch.compile` 约 **26.8 s**，`compile range (1,4096)`；
  - ACL graph 捕获 **1 个尺寸**，约 2 s、0.07 GiB；
  - 警告 `causal_conv1d_update_npu` 不可用、回退 PyTorch（本服务无 decode，未影响启动）。
- eager 对照：同一命令加 `--enforce-eager`，同 env、同端口，紧接 graph 服务之后启动。

## 2. 结果

30 次正式请求、10 次预热、C1：

| 请求 | 配置 | mean | p50 | p95 | p99 | dec/s |
| --- | --- | ---: | ---: | ---: | ---: | ---: |
| 307 | graph | 116.31 | 113.90 | 129.37 | 133.57 | 8.594 |
| 307 | **eager** | **109.95** | **106.93** | **123.36** | **128.51** | **9.091** |
| 967 | graph | 168.38 | 168.06 | 170.02 | 172.84 | 5.936 |
| 967 | **eager** | **168.20** | **167.30** | 171.67 | 177.14 | **5.942** |

- 307 token：graph mean **+5.8%**、p50 +6.5%、p95 +4.9%、吞吐 −5.5%，eager 明确更快；
- 967 token：graph mean +0.1%、p50 +0.5%、p95 **−1.0%**、p99 −2.5%，基本持平、方向混杂；
- graph 服务冻结 8 例 **8/8**，协议输出正常。

## 3. 解释

1. **pooling 不能使用 full graph**：vLLM 只允许 PIECEWISE；初版配置的 capture size 只有 `[1]`，307/967 token 实际未 replay；prefill 仍是 `torch.compile` 的动态图，不能像 decode 那样用固定 shape graph 消掉全部 dispatch。
2. **compile/graph 自身有开销**：307 token 的请求短，graph replay/分段/guard 成本高于省下的 dispatch；969 token 设备占比更高，graph 的收益被设备时间淹没。
3. **CPU dispatch 假设没有被 graph 兑现**：307 eager 每层约 2 ms 的 dispatch 仍在，但 graph 方案没有更快；说明瓶颈还包括 vLLM eager 模型内部的 Python/调度，而不是单纯 CUDA graph 能覆盖的 kernel 序列。
4. **A3 缺少 `causal_conv1d_update_npu`**：回退 PyTorch 会 stall decode-FULL；虽然本服务无 decode，但说明 graph 路径在当前栈上并不完整。

## 4. 采用决定

- **不采用 graph/ACL graph**：可运行、质量正常，但 307 更慢、967 无收益；保持 `--enforce-eager` 的提交配置。
- **不再投入 graph 调优**：pooling 的 full graph 被上游禁用，PIECEWISE + 动态 compile 对短/中请求没有帮助。
- **继续 joint head/pooler CPU 与 schema cache**：这两项是 307 残余里更直接的 host 成本；967 P95 仍以设备侧（MLP/INT8）为主。
- 证据：`Clef-27B/logs/gdn-data-path-20261115/graph-test/`、`eager-test/`、`restore-graph/`。

## 5. 服务恢复

## 6. 2026-11-16 复核：显式捕获 307/967 后的真实 replay

### 6.1 尺寸来源

固定版 Ascend 的默认捕获上限为 `min(max_num_seqs × decode_query_len, 512)`；S1 是 `max_num_seqs=1`，所以默认 `max_cudagraph_capture_size=1`，实际只捕获 1 token。307/967-token 请求超过捕获范围，dispatcher 返回 `CUDAGraphMode.NONE`，走 eager 路径。显式 `--compilation-config '{"cudagraph_capture_sizes":[307,967]}'` 会覆盖默认；捕获完成后，dispatcher 的 `_is_compatible` 允许请求 token 数小于等于捕获尺寸（graph 内补 padding），因此 307/967 都会 replay。

### 6.2 小尺寸捕获：307 有明显收益

`capture=[307,967]`，2 个 PIECEWISE graph，捕获约 3 s、0.24 GiB；30 次正式 + 10 预热、C1：

| 请求 | graph mean | graph p95 | 邻近 eager mean | 邻近 eager p95 |
| --- | ---: | ---: | ---: | ---: |
| 307 | **94.34** | **96.38** | 109.95–119.90 | 123.36–130.84 |
| 967 | 169.23 | 170.07 | 168.20–168.68 | 170.90–171.67 |

- 307 token：graph 快 **14–21%**（取决于对照窗口），证明短请求的 CPU dispatch 确实被 graph 消掉；
- 967 token：基本持平，设备计算占比更高，graph 不改变主瓶颈；
- 冻结 8 例：choice 全部不变，最大概率差 **1.65e-4**（score 题），不再是逐位一致。

### 6.3 全量 S1：粗桶和密桶都变差

**粗桶** `[256,307,384,512,768,967,1024,1536,1595,2048]`：10 个 graph，12 s、0.39 GiB，全量 2,352 题：

| 指标 | 粗桶 graph | eager BIC |
| --- | ---: | ---: |
| mean | 154.12 | 160.59 |
| p50 | 98.78 | 179.86 |
| **p95** | **244.53** | **198.42** |
| p99 | 251.52 | 204.70 |
| Capability | 74.2822 | 74.4255 |
| Calibration | 82.3329 | 82.7941 |
| Intelligence | 66.2315 | 66.0568 |
| accuracy | 1906/2352 | 1906/2352 |
| Score MAE | 0.401638 | 0.401389 |

- 质量：ΔCalibration −0.4612、ΔIntelligence +0.1747、ΔCapability −0.1433、accuracy 0，**四项均在 2PP 内**；4 条 choice 变化、max 概率差 0.1085；
- 性能：<384 token 的短桶 p50 85–97 ms，明显快；但 384+ 桶 p50 215–242 ms，把 **S1 P95 推到 244.53 ms**。

**密桶**（64-token 间隔，26 个 graph，30 s、0.50 GiB）：全量 2,352 题 mean 180.87、p50 228.73、p95 **265.80**、p99 280.99。密桶没有修复长请求，说明 384+ 的 graph 路径本身比 eager 慢，不只是 padding。

### 6.4 修正后的结论

- graph 的短请求收益真实存在，但 **S1 P95 由 384+ 请求主导**；捕获越密，长请求的 graph overhead 反而越明显；
- 质量在 2PP 内，但 graph 不再是逐位一致，且 S1 P95 从 198.42 退化到 244.53/265.80；
- **保持 eager 的提交配置**；不建议为 S1 继续投入 graph；
- 如果未来有“短请求 P50/均值”单独指标，可考虑只对 <384 token 捕获 graph、其余 eager；但这不会改善当前 S1 P95。
- 新证据：`Clef-27B/logs/gdn-data-path-20261115/graph-sizes-test/`、`graph-buckets-test/`、`graph-dense-test/`、`restore-graph-sizes/`。
