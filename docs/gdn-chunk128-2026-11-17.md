# GDN chunk 128 尝试（2026-11-17）

## 结论

- 之前 `chunk_size=128` 的 NaN 是**探针输入问题**：`shape_gdn_chunk_sweep.py` 用未归一化随机 q/k，而服务的 q/k 已经过 `ClefGdnQkvNorm` 做 L2Norm。用归一化 q/k 重测，128 **完全可用**：NaN=0，与 64 的差异仅 1 ulp（max_abs 4.88e-4）。
- 单算子收益：967 0.594→0.470 ms（−20.9%）、1,200 0.587→0.515（−12.3%）、1,595 0.675→0.587（−13.0%）、10,294 3.019→2.621（−13.2%）。
- 服务实现：`gdn_attn_builder.py` 的 `_GDN_CHUNK_SIZE=128` + `device_op.py` 决策分支 `chunk_size=128`。
- 全量 OD（host load 34）：mean 124.37 / p50 118.18 / **p95 164.20** / p99 202.24 ms、8.036 dec/s；相对 chunk 64 的 166.00，**p95 −1.80 ms（−1.08%）**。mean/p50 偏高是残余 host 负载影响。
- 质量：Capability **74.4113**、Intelligence **66.1169**、Calibration **82.7056**（三项 2PP 通过）；ERQA **217/400 = 0.5425**（与 chunk 64 相同，400/400 成功、0 重试，latency mean 219.6 / p95 311.6 ms）。但 OD 逐题 **9 条 choice 翻转、max 概率差 0.361、1,087 条 >1e-3**，远超此前 0.03/0.05 的逐题工程门槛。
- **2026-11-17 晚更新：已改为默认启用**。用户明确“2PP 以内就行”，`inference.py` 在决策 prefill 启用时自动 apply chunk128；`CLEF_GDN_CHUNK128=0` 回到 chunk 64。叠加 conv+QKV 融合后的同窗口 A/B：mean 120.926→118.733、p95 160.419→158.301（−1.32%）、8.259→8.411 dec/s；OD Capability 73.9636→**74.2476**、accuracy 1902→1904、ERQA 218→**216/400**（−0.50 pp）；S2 B8 C16 16.727 dec/s、Capability 73.8426。全部在 2PP 内。详见 `docs/gdn-conv-qkv-2026-11-17.md` 第 4.3 节。
- 官方入口（env on，host load 44+）全量 S1 为 mean 137.58 / p95 169.31 / 7.256 dec/s，受外部负载影响，不能与 chunk64 的 166.00 直接比较；低负载（load 34）launcher 为 124.37 / 118.18 / 164.20 / 8.036。最终 clean S1/S2 需等 host load 回落后执行；当前服务停止、源码 chunk64、端口空闲。

## 判断

- 逐题变化比之前被拒绝的 seqs4（4 条翻转、max 0.097）更大；虽然 OD 三项聚合在 2PP 内，但“保证质量”的工程门槛不通过。
- **官方两道质量门已全部通过**（OD 三项 2PP、ERQA 217/400 不变）；若比赛只按聚合 2PP、不设逐题门槛，128 已具备采用条件，只需接受 9 条翻转和 max 0.361 的逐题风险。
- 让 chunk 128 与 64 **逐位**一致需要重写 GDN 主核的 chunk 递推顺序，不是配置能解决的；当前不投入。
